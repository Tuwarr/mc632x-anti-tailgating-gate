# 动态二维码开门协议(MC632X demo)

适用双方:

- PC 端工具: `_build/qrtool/qr_tool.py`(Python 3.9 + tkinter + qrcode + pillow)
- 板端固件: MC632X + RT-Thread, 摄像头取帧 → zbar 解码 → 本协议解析校验 → PWM 舵机开门

开门有两条通道:

1. **动态二维码**(主通道): PC 窗口显示动态码 → 板上摄像头取帧 → zbar 解码 → HMAC-SHA256 验签 → 开门杆。
2. **TCP 命令**(辅助通道): PC 连板端 9000 端口发文本命令, 用于校时与远程开门(PC 按钮)。

---

## 1. 二维码载荷格式

一帧二维码内容为 1 行 ASCII 文本, 恰好 4 段, 以 `|` 分隔, 无换行符:

```
dooruser1|<ts>|<nonce>|<hmac_hex>
```

| 段 | 名称 | 长度 | 说明 |
|---|------|------|------|
| 1 | user | 固定 `dooruser1` | 用户标识, 本身也参与签名 |
| 2 | ts | 10 位十进制 | 生成时刻 Unix epoch 秒(UTC, 无时区偏移) |
| 3 | nonce | 16 位 hex 字符 | 一次性随机数(8 字节), PC 端每次刷新更换 |
| 4 | hmac_hex | 64 位小写 hex 字符 | HMAC-SHA256 摘要(见 §2) |

示例(真实帧, 见 `_build/qrtool/selftest.py` 自测输出):

```
dooruser1|1793290480|5dc1a02a4c660566|c558460dfac7170aecad3a065c89a79d414c1174531bf3576ca8dc15097bcf3c
```

- 总长约 103 字节, QR 纠错级别 M(约 15%), PC 端 `qrcode` 库生成, 白底黑码。
- PC 端每 **25 秒**换 nonce 重新生成并刷新(25 s < 30 s 时间窗, 保证屏幕上始终有有效帧)。
- 板端解析失败(段数≠4 / 段 2 非纯数字 / 段 3·4 长度不对)直接丢弃该帧。

## 2. HMAC 计算

- 算法: **HMAC-SHA256**
- 密钥: `DEMO_KEY = "mc632x-demo-key-2026"`(ASCII, 22 字节)。**量产必须改**(见 §8)。
- 被签名消息 = 前三段**原样拼接**(含 `|` 分隔符, 不含第 4 段 hmac 本身):

  ```
  msg = "dooruser1" + "|" + str(ts) + "|" + nonce
  ```

- 输出 32 字节摘要, 转为 **64 字符小写 hex** 填入第 4 段。

Python(PC 端, `qr_tool.py` 的 `sign()`):

```python
hmac.new(b"mc632x-demo-key-2026",
         b"dooruser1|1800000000|0123456789abcdef",
         hashlib.sha256).hexdigest()   # 小写
```

C(板端 mbedtls 参考写法):

```c
const mbedtls_md_info_t *md = mbedtls_md_info_from_type(MBEDTLS_MD_SHA256);
unsigned char digest[32];
mbedtls_md_hmac(md, key, key_len, msg, msg_len, digest);
/* digest[32] 逐字节转小写 hex(64 字符), 与第 4 段比较 */
```

### 固定测试向量(板端 mbedtls 联调对拍用)

由 `selftest.py` 第 [5] 步实机算出:

```
key  = mc632x-demo-key-2026
msg  = dooruser1|1800000000|0123456789abcdef
hmac = 0754111d7311154ec384fd3b89e95306e5f25f4326e54d2b4d5bfc490ccbbedb
```

板端用同样 key/msg 跑 mbedtls, 得到相同 64 hex 即链路打通。

## 3. 板端校验流程(建议顺序)

对每一帧 zbar 解码文本, 依次:

1. **格式**: 按 `|` 拆成恰好 4 段; 段 1 == `dooruser1`; 段 2 纯数字; 段 3 长度 16; 段 4 长度 64。
2. **签名**: 本地密钥对 `user|ts|nonce` 重算 HMAC-SHA256, 与段 4 做**常量时间比较**(先验签名、后做时间/查重, 避免未授权者借时序差异探测)。
3. **时间窗**: `|ts − board_now| ≤ 30`(见 §4)。
4. **nonce 查重**: 命中"最近已通过"列表则拒绝(见 §5)。
5. 全部通过 → PWM 舵机开门(建议开 N 秒后自动回位)。

任一步失败: msh 打印一行原因日志, 不开门。

## 4. 30 秒时间窗与板端时钟

- 有效窗: `|ts − board_now| ≤ 30` 秒。
- PC 端 25 s 刷新一次 ⇒ 任一时刻屏幕上的帧距其生成时刻 ≤ 25 s, 必落在 30 s 窗内; 摄像头解码+校验延迟(毫秒级)不构成风险。
- 板端无 RTC/NTP 时用**软时钟**: `board_now = uptime秒 + offset`:
  - 收到 `TIME <epoch>\n` 时记录 `offset = epoch − uptime`;
  - 板重启后 offset 归零 ⇒ 需重新校时才能通过时间窗(未校时时全部码被 §4 拒绝, 属预期行为)。

## 5. nonce 防重放

- 动机: 30 s 窗内同一帧码可被反复出示(录像/截屏重放), 时间窗本身挡不住。
- 板端维护"最近 60 s 内已通过校验的 nonce"表(建议环形缓冲, 容量 ≥ 8; 30 s 窗内 PC 最多产生 2 个不同 nonce, 余量充足)。
- 查表命中 → 拒绝; 通过校验 → 入表。仅清理 ts 已出窗的旧项。
- 表可只存 nonce 前 8 字节以省内存, 碰撞概率可忽略(演示场景)。

## 6. TCP 命令通道(端口 9000)

- 板端监听 **TCP 9000**(IP = 板子 192.168.137.100); 文本行协议, 命令以 `\n` 结尾; 建议同一时刻只接受 1 个连接, 收到完整一行即处理并回包。
- PC 端在**工作线程**里连接收发(3 s 超时), 失败仅弹窗提示, 不影响二维码刷新, 也不崩溃。

| 命令 | 含义 | 成功回复 | 失败回复 |
|------|------|----------|----------|
| `TIME <epoch秒>\n` | 校板端软时钟(§4 的 offset) | `OK\n` | `ERR <reason>\n` |
| `OPEN\n` | 远程开门(不走二维码校验链) | `OK\n` | `ERR <reason>\n` |

- 二维码时间窗依赖校时: 首次联调先点"校时"再出示二维码。
- 该通道**无鉴权**, 仅适用于开发内网直连; 若将来暴露到更大网络, 需加同样的 HMAC 签名。

## 7. 降级开关: 板时钟不可信时跳过时间窗

板端建议在应用配置头文件(如 `app_qr.h`)放宏:

```c
#define QR_EN_TIME_WINDOW   1   /* 1=启用 30s 时间窗(默认, 安全);
                                   0=调试用: 跳过时间窗比对, 板子没校时时也能开门 */
```

- 置 0 时: 只验格式 + HMAC + nonce 查重, **不比对 ts** —— 板端时钟未校准也能联调开门。
- 风险: 攻击者拿到任意一帧历史码即可在 nonce 未入表时开门 ⇒ **仅限调试, 上线前必须恢复为 1**。
- nonce 防重放(§5)不受该宏影响, 始终生效。
- 若调试期还想连 nonce 查重一起关(仅排查用), 建议另设 `QR_EN_NONCE_CHECK`, 同样只许调试期置 0。

## 8. 密钥与量产注意

- `DEMO_KEY = "mc632x-demo-key-2026"` 为演示密钥, **量产必须改**; 建议每台设备唯一, 存放于安全存储区而非源码常量。
- 换钥时需同步修改: PC 端 `qr_tool.py` 顶部 `DEMO_KEY` 与板端密钥存放处, 并重算 §2 测试向量。
- 本协议为演示级: 单用户、单密钥、无证书; 量产应评估密钥轮换与用户级授权。
